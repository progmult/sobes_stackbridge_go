# Subscriptions API

REST-сервис для агрегации данных об онлайн-подписках пользователей.

Go 1.25, PostgreSQL 16, chi, pgx, golang-migrate, swaggo.

## Запуск

```bash
cp .env.example .env && docker compose up -d --build
```

Значения в `.env.example` рабочие, менять ничего не нужно. Сервис поднимется
на `http://localhost:8080`, миграции применятся автоматически при старте.

```bash
curl http://localhost:8080/healthz
```

Swagger UI: <http://localhost:8080/swagger/index.html>

Остановить (`-v` дополнительно удалит данные БД):

```bash
docker compose down
```

Если порт 8080 или 5432 занят, поменяйте `HTTP_HOST_PORT` / `POSTGRES_HOST_PORT`
в `.env`.

## API

Базовый путь — `/api/v1`. Даты передаются строками в формате `MM-YYYY`,
стоимость — целое число рублей.

| Метод | Путь | Описание |
| --- | --- | --- |
| `POST` | `/api/v1/subscriptions` | создать подписку |
| `GET` | `/api/v1/subscriptions/{id}` | получить подписку |
| `PUT` | `/api/v1/subscriptions/{id}` | обновить подписку |
| `DELETE` | `/api/v1/subscriptions/{id}` | удалить подписку |
| `GET` | `/api/v1/subscriptions` | список подписок: фильтры `user_id`, `service_name`, постранично |
| `GET` | `/api/v1/subscriptions/summary` | суммарная стоимость за период |
| `GET` | `/healthz` | проверка доступности сервиса и базы |

### Создание

```bash
curl -X POST http://localhost:8080/api/v1/subscriptions -H 'Content-Type: application/json' -d '{"service_name":"Yandex Plus","price":400,"user_id":"60601fee-2bf1-4721-ae6f-7636e79a0cba","start_date":"07-2025"}'
```

Ответ `201 Created`:

```json
{
  "id": "524ef7dd-25b0-47c0-813d-d011b6595232",
  "service_name": "Yandex Plus",
  "price": 400,
  "user_id": "60601fee-2bf1-4721-ae6f-7636e79a0cba",
  "start_date": "07-2025"
}
```

`end_date` необязательное: если его нет, подписка считается бессрочной.
В ответе на `201` приходит заголовок `Location` с адресом созданной записи.

### Список

```bash
curl 'http://localhost:8080/api/v1/subscriptions?user_id=60601fee-2bf1-4721-ae6f-7636e79a0cba&limit=2&offset=0'
```

```json
{
  "items": [ { "id": "...", "service_name": "Netflix", "price": 1000, "user_id": "...", "start_date": "01-2025", "end_date": "03-2025" } ],
  "total": 5,
  "limit": 2,
  "offset": 0
}
```

`limit` по умолчанию 50, значения больше 200 урезаются до 200; `offset` по
умолчанию 0. `total` — сколько всего записей подходит под фильтр, без учёта
постраничности: по нему клиент считает количество страниц. Ответ обёрнут в
объект, а не отдан голым массивом, именно чтобы рядом с данными поместились
эти поля. Сортировка включает `id` последним ключом — без него записи с
одинаковой датой могли бы менять порядок между страницами и часть из них
терялась бы.

### Суммарная стоимость

```bash
curl 'http://localhost:8080/api/v1/subscriptions/summary?from=01-2025&to=12-2025&user_id=60601fee-2bf1-4721-ae6f-7636e79a0cba&service_name=Yandex%20Plus'
```

```json
{ "total_price": 2400, "from": "01-2025", "to": "12-2025" }
```

Период `[from, to]` включает оба крайних месяца. Для каждой подписки берётся
пересечение её срока с периодом, число месяцев умножается на месячную
стоимость. Подписка без `end_date` считается активной до конца периода.
Параметры `from` и `to` обязательны, `user_id` и `service_name` — нет.
Считается всё одним SQL-запросом, без выгрузки записей в приложение.

### Ошибки

Единый формат: машиночитаемый `code` для обработки на клиенте и
человекочитаемое `message` на русском.

```json
{ "code": "validation_error", "message": "некорректный запрос: стоимость подписки не может быть отрицательной" }
```

| Код ответа | `code` | Когда |
| --- | --- | --- |
| `400` | `validation_error` | некорректные данные запроса |
| `404` | `not_found` | подписки или маршрута не существует |
| `405` | `method_not_allowed` | метод не поддерживается этим маршрутом |
| `413` | `payload_too_large` | тело запроса больше 1 МБ |
| `415` | `unsupported_media_type` | `Content-Type` не `application/json` |
| `500` | `internal_error` | внутренняя ошибка, детали только в логе |
| `503` | `unavailable` | база данных недоступна (только `/healthz`) |
| `504` | `timeout` | превышено время обработки запроса |

Ошибки маршрутизации и паника внутри обработчика тоже приходят в этом формате,
а не пустым ответом или текстом от роутера.

В `message` не попадают внутренние детали: имена Go-структур, их полей и типов,
текст стандартной библиотеки, коды SQLSTATE. Ошибка разбора JSON переводится в
свою формулировку, а исходная попадает в лог отдельным атрибутом `cause` —
санировать ответ не значит терять диагноз. Имена полей в сообщении — те, что
прислал сам клиент, их показывать можно.

Тело запроса ограничено 1 МБ. Отсутствующий `Content-Type` допускается — часть
клиентов его не ставит, — а чужой тип отвергается с `415`. Отмена запроса
клиентом не считается отказом сервиса: она пишется на уровне `info` и не даёт
`500`.

Валидация в Go повторяет ограничения колонок в схеме (`INTEGER` для стоимости,
`VARCHAR(255)` для названия), а ошибки Postgres с кодами нарушения ограничений
дополнительно переводятся в `400`. Иначе ошибка в запросе клиента возвращалась
бы как `500`, хотя сервер отработал верно.

Каждая строка лога содержит `request_id`, общий для строки доступа и для строки
об ошибке — по нему они сопоставляются при разборе инцидента.

`/healthz` живёт вне `/api/v1` и в swagger намеренно не вынесен: swagger
склеивает пути с `basePath` и в UI запрашивал бы несуществующий
`/api/v1/healthz`.

Сообщения об ошибках и логи — на русском. Машиночитаемые части остаются
английскими: значения `code`, имена полей JSON и ключи атрибутов в логах
(`error`, `user_id`, `status`) — по ним фильтруют и грепают, переводить их
нельзя.

### Идемпотентность

`GET`, `PUT` и `DELETE` идемпотентны, как того требует HTTP:

- **`PUT`** полностью перезаписывает запись, поэтому повторный запрос с тем же
  телом даёт тот же результат и тот же `200`. Именно поэтому здесь `PUT`, а не
  `PATCH` с частичным обновлением.
- **`DELETE`** при повторном вызове отвечает `404` вместо `204`, но состояние
  сервера после первого и после третьего вызова одинаковое — записи нет. HTTP
  требует одинакового эффекта, а не одинакового кода ответа.
- **`POST`** не идемпотентен: два одинаковых запроса создадут две записи. Это
  поведение по спецификации, а не недосмотр.

Если бы бизнес-требования запрещали дубли, вариантов два: заголовок
`Idempotency-Key`, по которому сервер запоминает ответ на первый запрос и
повторяет его вместо создания новой записи, либо уникальный индекс по
`(user_id, service_name, start_date)`. Ни то, ни другое в ТЗ не требуется,
а уникальный индекс ещё и запретил бы легальный сценарий с двумя подписками на
один сервис — поэтому не добавлено осознанно.

## Структура

```
cmd/api                     точка входа: конфиг, миграции, роутер, graceful shutdown
internal/config             настройки из переменных окружения
internal/model              модель подписки, валидация, формат даты MM-YYYY
internal/service            бизнес-логика, интерфейс Repository
internal/storage/postgres   пул соединений, миграции, SQL-запросы
internal/transport/rest     роутер, обработчики, DTO
migrations                  SQL-миграции, встроены в бинарь через embed
docs                        swagger, генерируется из аннотаций
```

Хендлер знает про сервис, сервис — про модель и интерфейс `Repository`,
реализация которого лежит в `storage/postgres`. Благодаря интерфейсу сервис
тестируется без базы.

Как устроено внутри и почему именно так — в [ARCHITECTURE.md](ARCHITECTURE.md):
направление зависимостей, путь запроса, разделение валидации между слоями,
обработка ошибок, а также перечень того, что намеренно не сделано.

## Конфигурация

Все настройки — переменные окружения, список с рабочими значениями лежит в
[.env.example](.env.example). Сам `.env` в репозиторий не коммитится.
`docker compose` подставляет значения из `.env`, а при его отсутствии
использует дефолты из `docker-compose.yml`.

## Миграции

Лежат в [migrations](migrations) обычными SQL-файлами `up`/`down`, встроены в
бинарь через `embed` и применяются самим сервисом при старте (golang-migrate,
версия хранится в таблице `schema_migrations`). Повторный запуск ничего не
меняет.

### Индексы

Оба фильтра из ТЗ покрыты индексами, это проверено планами запросов на 200 000
записей:

- `subscriptions_user_id_idx` по `user_id` — фильтр по пользователю в списке и
  в подсчёте суммы;
- `subscriptions_service_name_idx` по **выражению** `lower(service_name)` —
  сравнение идёт без учёта регистра, и обычный индекс по колонке для него не
  применился бы. Без этого индекса оба запроса шли последовательным сканом всей
  таблицы, с ним — `Bitmap Index Scan`.

Чтобы индексы действительно применялись, условия `WHERE` собираются в Go из
тех фильтров, которые заданы, а не пишутся один раз в виде
`$1 IS NULL OR user_id = $1`. Универсальный вариант позволил бы обойтись
статическим SQL, но на generic-плане планировщик обязан построить план, годный
для обеих веток, и индексом воспользоваться уже не может — выборка вырождается
в перебор всей таблицы (замерено: 10 мс против 0.1 мс на 200 000 записей).
В SQL подставляются только номера плейсхолдеров, значения всегда уходят
параметрами.

Индекса под сортировку списка (`start_date DESC, id`) намеренно нет. Он ускоряет
первую страницу с 15 мс до 0.03 мс, но весит 8 МБ при 25 МБ данных — это
крупнейший индекс схемы ради порядка сортировки, который ТЗ не задаёт, плюс
расход на каждой записи. При ожидаемых объёмах не окупается; если понадобится,
добавляется одной строкой в новой миграции.

## Разработка

Для запуска сервиса Go не нужен — всё собирается внутри `Dockerfile`. Команды
ниже нужны только при работе над кодом и требуют установленного Go.

**Юнит-тесты** покрывают разбор формата `MM-YYYY`, валидацию подписки, проверку
периода и весь HTTP-слой через `httptest` — разбор тела и query, постраничность,
маппинг ошибок в коды ответа, поведение при панике. Базу данных они не трогают:
и репозиторий, и проверка доступности БД подменяются заглушками, поэтому тесты
проходят за миллисекунды.

**Интеграционные тесты** проверяют то, что заглушками не проверишь: расчёт суммы
за период целиком живёт в SQL. Пересечение срока подписки с периодом, число
месяцев в нём, бессрочная подписка, оба фильтра, регистронезависимое сравнение
названия, а также round-trip записи и постраничность списка проверяются на
настоящем PostgreSQL. Базу поднимает `testcontainers-go`: одноразовый контейнер
на время прогона, те же миграции, что и в сервисе, и гарантированная остановка
после — ни боевая, ни общая тестовая база не задействованы.

```bash
go test ./... -count=1
```

Отдельной команды не нужно: если docker доступен, интеграционные тесты идут в
общем прогоне (первый запуск дольше — тянется образ `postgres:16-alpine`); если
нет — они помечаются как пропущенные, и прогон всё равно зелёный.

Статический анализ:

```bash
go vet ./...
```

Папка `docs/` целиком генерируется из аннотаций в коде и руками не правится —
это отражено в [.gitattributes](.gitattributes). В репозиторий она
коммитится, потому что `docs/docs.go` — обычный Go-пакет, который импортирует
роутер: без него проект не соберётся после `git clone`.

Перегенерировать swagger после правки аннотаций в коде:

```bash
go run github.com/swaggo/swag/cmd/swag@v1.16.6 init -g cmd/api/main.go -o docs
```

Те же команды собраны в [Makefile](Makefile): `make test`, `make vet`,
`make swagger`, `make up`, `make down`, `make logs`.
